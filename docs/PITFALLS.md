# 踩过的坑与硬性纪律

> 更新：2026-10-07 · 每条都标了**代价**，因为没有代价的教训不会被记住。

这份文档是给**动手之前**读的。里面每一条都是真实翻车记录。

---

## A. 探索与查证（最重要的一节）

### A1. 枚举，不要猜名字 ⭐ 最贵的教训

**连续错了四次**，全是同一个错误：

| 我猜的 | 实际 |
|---|---|
| `m_MapTex` | 不存在。只有 `m_MiniMap` / `m_TOCTexture` |
| `Localization`（当类型名） | 类型存在但成员名不对 |
| `m_LocalizedName` | 被 interop 剥掉了 |
| `Il2Cpp.Locale.GetText` | 存在，但**原样回显参数**，不翻译 |

**正确做法**：遍历程序集，**在所有静态 `(string)->string` 成员上调用已知 key 试**，
最后才找到 `Il2Cpp.Localization.Get`。

> **代价**：四轮往返。而且每次"猜错"之后我又猜了一个，而不是改方法。

### A2. 搜字符串不等于类型存在

反向也栽过：**面板用 NGUI，它的文字在 `UILabel` 上，不是 `UnityEngine.UI.Text`**。
我按 `UnityEngine.UI.Text` 搜面板标签，**找到 0 个**，还一度以为面板没有文字。

**正确做法**：先确认 UI 框架（这个游戏是 **NGUI**：`UISprite` / `UITexture` / `UILabel` / `UIAtlas`），
再按对应类型找。Unity 的两套 UI 系统**互不相通**。

### A3. 导出/测量工具**不要**做"文件存在就跳过"

抓取面板贴图时我写了"存在则跳过"，结果留了一张**点亮地图之前**的迷雾图。
之后一整轮排查都在分析那张错图，得出了错误结论。

**规则**：测量与导出**永远覆盖**。要保留历史就用时间戳命名，不要用"存在即跳过"。

## B. IL2CPP / Unity 的硬性约束

### B1. 异常本身**就是**性能问题 ⭐

**症状**：打开全屏地图后指针跟随变慢，看起来像"渲染慢"。
**真因**：日志里 **377 次 `NullReferenceException`，每帧一次** —— 悬停提示的对象创建失败，
每次都重新抛一遍。Unity 里异常的代价极高。

> **代价**：我按"渲染/对象数"方向查了很久。**用户一句"不悬停就不该有性能问题"
> 才把我推回正确方向。**

**纪律**：看到卡顿，**先去日志里数 `Exception`**。别只把异常当错误信息。

### B2. UI 组件列表**不能随意加**

给 tooltip 的对象加了 `Image`（想要深色底片）之后，**`Text` 组件再也建不出来**。

- 原样（`RectTransform` + `CanvasRenderer` + `Text`）→ 正常
- 加上 `Image` → `GetComponent<Text>()` 返回 **null**
- 改成**分步** `AddComponent<Text>()` → **也返回 null**
- 改成**按 `Il2CppType` 加** → **还是 null**

三种写法全部失败。**唯一可行的是回到原来那个组件列表。**

**修法**：底片做成**独立的对象**，放在文字后面。

> **代价**：返工五轮。**用户的线索"加描边前那版能悬停"才定位到** ——
> 我该先去看能工作的那版代码，而不是逐个试新写法。

**纪律**：**能工作的配置是已知量。改它之前先单独验证那一处改动。**

### B3. UI 按层级顺序绘制 ⭐

uGUI **后面的盖前面的**。

悬停提示是最早创建的，而 802 个标记是后来一个个加上的 ⇒ **提示框一直被压在标记下面**。
表现是"有时候被图标盖住" —— 其实是**标记密的地方必然被盖住**。

**修法**：显示时 `SetAsLastSibling()`。

### B4. 每帧写 UI 值会触发重建

`anchoredPosition` / `sizeDelta` / `text` / `fontSize` —— 即使**赋相同的值**也会标脏
layout 或 text mesh。802 个标记 × 每帧 2 次写 = 拖拽像慢一拍。

**纪律**：每帧更新的 UI 值一律写成：
```csharp
if (rect.anchoredPosition != position) rect.anchoredPosition = position;
```

### B5. `Outline` 把顶点数翻五倍

`Outline` 会为**每个字形**再画 **4 份**副本。给几百个 CJK 标签加它 = 顶点爆炸。

**改用 `Shadow`**（1 份额外副本），效果接近、代价是五分之一。

### B6. 原版底图的上限是 1024×1024

**已枚举确认**：`RegionSpecification` 只暴露 `m_MiniMap` 与 `m_TOCTexture`（都是 1024 DXT5），
prefab 内的贴图是 `null`，**不存在更大的区域贴图**。

要真底图只能**从面板抓**（面板画的是 2048）。**不要再去枚举一遍。**

### B7. 软边贴图不能用 alpha 阈值界定内容范围

`MeasureOpaqueUv` 在**硬边留白**（letterbox）上可靠，在**羽化边**上不可靠 ——
阈值取 8 和取 200 得到的框**相差超过 10%**。

> **代价**：据此推错了一整轮，把羽化边缘当成了内容边界。

**纪律**：先确认图是硬边还是软边，再决定能不能用阈值。

## C. 本项目的具体陷阱

### C1. 构建 key 的格式：组装处与解析处必须一起改

标记构建 key 是 `"场景名|标记来源|投影|条目数"`。

限流判定曾经**只比对条目数**（`EndsWith("|" + count)`），于是切图源时
key 变了但"结尾还是 `|816`" ⇒ 判定"无事可做" ⇒ **标记带着原版的 uv 画在社区图上**。

**修法**：投影变化**立即重建**（它让每个位置都失效），只有同投影下的条目数变化才限流。

> **代价**：用户发现并报告（"标记全是偏移的，用的应该不是社区地图的坐标"）。

### C2. `LoadMapElementsForScene` 会 **APPEND**

调两次就是**双份标记**。所以 `_elementsLoadedForScene` 是**全局唯一闸门** ——
`MapLayer` 里那个同名字段只是状态记录，**不授权第二次调用**。

### C3. 游戏**不删除**已采集的标记

这是本模组做标记重写的动机之一。
`m_HarvestablesForMapVisibility` 只覆盖 **136 / 802** 条，**不足以**当通用判据。

### C4. `m_IsSurveyed` **不是**可见性判据（已证伪）

**实测**：802 条里 **765 条三个标志全为 false**（`surveyed` / `unlocked` / `discovered`），
而游戏照样实例化了 162 个图标。

⇒ 按 `surveyed || unlocked` 绘制会**丢掉 125 个标记**。
⇒ 目前是"全画 802 + 玩家用 5 类筛选"，这是**刻意的取舍**。

> **代价**：旧手册把它写成了设计条款，**照做就丢标记**。

### C5. 社区地图**不是 1:1** 画的

用 5 个校准点算两轴比例：**X 2.04 px/单位，Z 1.76 px/单位 —— 差 16%**。

⇒ 社区图路径**精度有天花板**，加校准点无法根治。

### C6. 原版地图**不能**去拟合

**社区图是按原版图对齐的，反过来不成立。**
原版必须保持**绝对精确** —— 这是用户明确的要求。

### C7. 标记图集是**白色图案**

游戏绘制自己的地图时会**另加色调**。我们直接用原图就是白的。

**而且单色无解**：社区图的图标**画死在图里、随缩放变化**，而我们的标记是**固定屏幕尺寸**。
白色在缩小看时铺满奶油底而消失，深色在放大看时糊进深色地形成一片黑。

⇒ 现在的做法是**图标 + 深色垫底描边**（可关）。

### C8. 设置文件是 `Mods\CommunityMinimap.json`

**不是 `Loader.cfg`**。字段名就是 JSON 键。
`ModSettings` **未暴露存档路径**，所以**旧键无法写迁移** —— 只能忽略。

### C9. 游戏进程名是 `tld`

不是 `TheLongDark`。`build.ps1` 靠这个名字判断能否安装。
注意它**在检查进程之前不理会 `-SkipInstall`**，所以游戏运行时无法绕过。

### C10. 日志路径

`<游戏目录>\MelonLoader\Logs\*.log`，**按时间排序取最新的**。
**没有 `Latest.log`** —— 不要去找它。

### C11. `scene` 不是无害的传送命令

实测 `scene 场景名` 会绕过正常过图和目标区域的存档恢复，可能让区域、容器、探索状态和动态物件
看起来像第一次加载；之后自动保存还可能把这份状态写回存档。

**纪律**：`scene` 只用于一次性测试档。正式校准自然过图进入目标场景；同一室外场景内才使用 `tp`。

### C12. 一张 Unity 场景不一定只有一张地图

`MineTransitionZone` 同时包含沿海公路下层和煤渣山矿洞上层，场景名完全相同，只能靠玩家 Y 区分。
反过来，多楼层组合图也不一定能用一个 X/Z 仿射矩阵表达。

**纪律**：遇到图不匹配，先记录 `scene + (x,y,z)`，不要只按场景名强绑。能按稳定高度/范围区分时用空间变体；
不能稳定区分时保持探针状态，不发布错误指针。

## D. 工作方式的纪律

这些是元层面的，但每一条都对应真实返工。

### D1. 先量再改 ⭐

**用数字对账，不要"看着对"。**

我做分割器时**调试了六轮**，四个 bug（括号深度、注释跨空行、从空行取名、正则贪婪），
每次都是"看着对"就往下走，**直到用数字对账才发现不对**。

**具体做法**：
- 拆分后用验证脚本比对成员（"230 个成员，0 缺失，0 新增，0 内容变化"）
- 改颜色/位置前先量出实际数字（"33 种唯一图标"）
- 声明"已修复"时要能指出日志行

### D2. 加功能前先想清影响范围

**悬停功能返工七轮**，每次都是"改 A 顺手弄坏 B"：

| 我加的 | 顺带弄坏的 |
|---|---|
| `Image` 底片 | `Text` 组件建不出来 |
| `Outline` 描边 | 顶点爆炸、性能崩塌 |
| 悬停逻辑 | 地名被隐藏、小地图地名不动 |
| 悬停选取 | 悬停在地名上也弹框 |
| 深色色调 | 深色地形上糊成一片 |

**动手前问一句**："这个改动还会碰到什么？"

### D3. 一次只改一样

我一次性加了**三样**（描边 + 底片 + 字号），定位花了五轮。
**一次只加一样，一轮就能定位。**

### D4. 遇到矛盾时，退一步检查**方案本身** ⭐

改标记颜色错了两轮：

1. 深色配羊皮纸 —— **方向反了**
2. 还写了一段解释，把错误包装得很合理
3. **第三次才想到质疑"单色"这个框架本身**

点破我的都是**用户的一句常识性反问**：「白色配白底?」「图标不是就那几个吗?」

> **倾向**：遇到矛盾时，在**既定方案里找补**，而不是检查方案对不对。

### D5. 写解释的能力 ≠ 判断正确 ⭐

第 2 轮我为错误的配色**写了一段看起来很有道理的解释**（"游戏图标是深色所以深色配浅底"）。
用户因此多绕了一轮。

**一段流畅的说明，可能只是把错误包装得更可信。**
**先验证，再解释。**

### D6. 能工作的配置是已知量

见 B2。**改动已知可工作的东西之前，先单独验证那一处改动。**

### D7. 文档滞后于代码

旧手册 3654 行里，**「待做」标记大面积过时** —— §30/§33/§34/§37 描述的"待做"其实已完成，
而 §37.2 的一条设计**照做会删掉整个地名图层**（我照做了，所以地名全没了）。

> **纪律**：看到"待做/未验证/下一步/设计"，**先到代码里确认是否已经做了**。

### D8. 不要把"文件大"当成"要拆"的理由

`ModEntry.cs` 5134 行时，真正的病是**两处**：`OnUpdate` 267 行，
以及字段级共享（`_mapRect` 被 11 个功能区访问）。

**"共享状态"是事实，不是缺陷。** `partial class` 拆文件解决的是"找代码难"，
**不解决耦合** —— 拆完字段还是共享的。

### D9. 危险的批量操作要能证明安全

我用脚本批量转换行尾，**两次损坏了 8 个已入库的 PNG**（都从 git 恢复了）。
根因：我把 git 的 `binary` 属性语义**搞反了两次**
（`binary: unspecified` 是**文本**，`binary: set` 才是二进制）。

**最终结论**：这个手工批量操作**根本就不该做** —— `.gitattributes` 一条规则就够了，
git 会自动规范化。**删掉了脚本。**

**纪律**：批量改二进制/文本混存的目录时，**先确认判定依据，再小范围试**，
并且**先备份或确保可以从 git 恢复**。
